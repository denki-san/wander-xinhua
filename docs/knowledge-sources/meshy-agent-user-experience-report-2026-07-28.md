# Meshy Agent 用户使用情况简报

- Date: 2026-07-28
- Scope: Meshy Agent 网页模式，不讨论 API
- Evidence: 一次 3 件试跑、一次 10 件完整生产批次、15 个原始/备选/失败 GLB
- Evidence snapshot: `2026-07-28-meshy-agent-ux-report-2ca6310`
- Position: 适合创意探索和候选模型生成；目前还不是可靠的生产型 3D Agent

## 一句话结论

Meshy Agent 最大的问题不是“偶尔生成不好”，而是对话、任务状态、当前源模型、
实际参数、credits 和最终下载文件没有形成一个可信的单一真值。用户必须不断离开
对话，到 Viewer、资产库、下载文件和 Blender 中交叉确认。

证据边界：下列 1–10 项来自本轮实际使用；每项“建议”是产品判断；竞品部分只引用
官方公开能力，没有做同等规模实测，也没有采用社区口碑推断质量排名。

## 主要问题

### 1. Agent 对自身产品能力的回答不可靠

实际使用中，Agent 曾表示页面没有某些模型偏好、尺寸和原点设置，但真实 UI 中存在。
这会让用户无法判断应该相信回答还是相信界面。

建议：Agent 回答产品能力时直接读取当前账号和当前页面配置；无法读取就明确说
“未确认”，不要凭语言模型记忆回答。

### 2. “已经发送”和“已经执行”不够明确

有时文字已经填入输入框，但任务并未提交；真正开始后才会出现输入框清空和 Stop
状态。用户很容易误以为任务已经运行。

建议：增加明确的任务卡状态：`待提交 / 已排队 / 处理中 / 等待审核 / 已完成 / 失败`，
并给每次操作独立 task ID。

### 3. 人工审核节点只是聊天约定，不是产品机制

正确流程应该先生成图片、人工确认，再生成 3D。但目前主要依赖用户在提示词里要求
“生成图片后停止”。`Skip` 等自然语言还可能被误解成继续旧任务。

建议：在图片结果上提供明确的“批准并生成 3D”“要求修改”“拒绝”按钮。未经批准，
Agent 不得消耗 3D credits。

### 4. 长对话和批量任务容易发生上下文串线

本次出现过旧 Viewer、旧模型卡片和当前任务不一致的情况；第二轮 Remesh 也曾关联到
错误源卡片。最终下载还曾得到错误的自行车文件。

建议：每个结果必须显示完整 lineage：

`输入图片 → 初始 3D → Remesh 版本 → 当前 Viewer → 导出文件`

不能只靠聊天顺序和高亮状态表达继承关系。

### 5. Agent 的完成报告可能与真实模型数据不一致

Agent 曾把一批初始模型统一描述为约 `10,000 tris`，但 Viewer 和导出 GLB 的实际值
各不相同。文字总结听起来确定，却不足以用于生产决策。

建议：回答中的 triangles、vertices、纹理数量、尺寸和 credits 必须直接绑定后台
任务数据；无法读取时不要生成近似数字。

### 6. Remesh 过于像“一个数字滑杆”

降低边数对石桩、花箱等粗实体有效，但会破坏树枝、灯杆、伞面、自行车车架和垃圾桶
箱体。提高目标面数也不一定恢复断裂结构。

建议：Remesh 前先识别几何类别，提供不同策略：

- 粗实体：允许积极降面；
- 条板和组合件：以缝隙、落地点和独立构件为保护条件；
- 细杆、薄片、轮组：默认保结构，并在检测到破洞或断裂时阻止覆盖原版本。

### 7. 缺少“模型实际用途”这一层参数

当前可以设置高度和面数，但游戏资产还需要典型观察距离、最大实例数、第二尺度、
原点、墙面锚点、材质数和文件体积预算。同一个模型用于近景 Hero 和重复街具，参数
不应相同。

建议：生成前增加用途预设，如“移动端重复街具”“WebGL 近景道具”“3D 打印”，并
把对应预算转成可见的任务合同。

### 8. Credits 缺少操作前后的明确回执

官方已经列出不同 Agent 操作的 credits 成本，但在长对话中，用户仍很难快速知道
下一步会花多少、刚才哪一步花了多少、失败或重试是否退款。

建议：每个会收费的按钮或 Agent 动作执行前显示成本确认，完成后生成不可变费用回执；
批量任务先显示总成本上限。[Meshy credits 规则](https://help.meshy.ai/en/articles/15643245-when-were-my-meshy-credits-used-or-refunded)

### 9. 下载和交付缺少可靠回执

本次 Chrome 下载被 `ERR_BLOCKED_BY_CLIENT` 拦截，Viewer 弹窗叠加又可能导出错误
对象。单纯显示“下载成功”不能证明本地拿到的是当前模型。

建议：下载完成后显示文件名、格式、字节数、模型版本、导出参数和 checksum；支持从
任务卡重新下载同一不可变版本，而不是依赖当前 Viewer 状态。

### 10. 纹理成本不够显眼

旧自行车只有约 2,789 tris，但因为四张 4096² PBR 图片达到 53.3 MiB。用户如果只看
边数，会误判它很轻。Meshy 官方也说明 GLB 会嵌入纹理，且导出不会主动压缩生成时的
纹理分辨率。

建议：在 Viewer 和下载页同时显示 geometry、images、texture resolution、estimated
GLB size；提供“无纹理 / 共享色板 / 单张 Base Color / 完整 PBR”明确选择，而不是
默认把纹理当作免费附属物。[Meshy 纹理导出说明](https://help.meshy.ai/en/articles/15724161-how-to-export-meshy-models-with-colors-and-textures)

## 与同类产品的轻量对照

以下只比较官方公开的工作流和控制方式，没有对它们做同等规模实测：

- Tripo 的文字生成说明同样采用“先生成并确认参考图，再转 3D”，其 CLI 还显式提供
  `--out`、等待和自动下载等任务控制。它说明 Agent 模式不必牺牲确定性的任务输出。
  [Tripo 文字转 3D](https://www.tripo3d.ai/features/text-to-3d-model)
  [Tripo CLI](https://developers.tripo3d.ai/en/docs/cli)
- Rodin 把 multi-view 的 `concat/fuse`、mesh mode、质量、材质和面数作为明确参数。
  这种“先形成可见合同，再执行”的方式更适合生产。
  [Rodin Gen-2 参数](https://developer.hyper3d.ai/api-specification/rodin-generation-gen2)
- Sloyd 强调生成式 AI 与参数化模板结合。对路灯、长椅、垃圾桶等重复资产，模板化
  控制通常比每次重新猜完整网格更可预测。
  [Sloyd Text-to-3D](https://www.sloyd.ai/text-to-3d)

Meshy Agent 的优势仍然明显：自然语言入口友好、可以连续完成图片、3D、Remesh 和
纹理操作，也适合统一风格的批量探索。官方本身将其标为 Beta，并承认复杂多步骤流程
可能更慢、结果可能需要人工修正。[Meshy Agent 入门](https://help.meshy.ai/en/articles/15297780-getting-started-with-meshy-agent-beta)

## 建议优先级

### P0：先解决可信度

1. 明确任务状态和 task ID；
2. 图片到 3D 的强制审核门；
3. 完整模型 lineage；
4. 参数、统计和费用必须来自真实任务数据；
5. 下载生成不可变交付回执。

### P1：再提高生产效率

1. 按几何类别选择 Remesh 策略；
2. 增加游戏用途、真实尺寸和实例预算；
3. 提供版本并排对比与结构异常提示；
4. 批量任务显示逐件状态、成本和失败恢复入口。

### P2：最后扩展自动化

提供结构化任务清单、Webhook/CLI/DCC Bridge 或可下载 manifest，让外部 Blender、
游戏引擎和资产管理系统能确认“用了哪个输入、哪个版本、哪些参数、得到哪个文件”。

## 最终评价

从普通创作者角度，它已经是好用的创意助手；从游戏资产生产角度，它目前更像“会操作
Meshy 功能的聊天层”，还不是能独立承担质量、成本和交付责任的生产 Agent。下一阶段
最值得投入的不是让回答更像人，而是让每句话都能对应一个真实任务状态和可验证产物。
