# Wander Xinhua：第三人称相机、碰撞与移动端摇杆优化研究

- 研究日期：2026-07-24
- 目标：解决探索态中建筑密集区域的相机遮挡/裁剪、视野偏窄、移动端摇杆转向不跟手，并给出可回滚的实施顺序。
- 范围：现有 React Three Fiber 场景与独立 `Threejs-3d-research` Wiki；不在本研究中替换为完整物理引擎或直接引入外部控制器。

## 先给结论

应保留现有“显式地图边界 + 可解释建筑碰撞”的主路线，但将探索相机改造成明确的 **pivot → spring arm → camera** 三层状态机：

1. 相机碰撞只压缩臂长，不在每一帧改选任意侧向兜底机位；
2. 碰撞检测从“二维端点 + 视线”升级为“相机体积的连续扫掠”；
3. 相机被压到最短距离时，用局部遮挡淡出补足可见性，而不是继续把镜头塞进角色头部；
4. 摇杆移动每帧相对当前相机平面计算，移除持续推杆时冻结首次相机朝向的行为；
5. FOV 作为按视口验证的镜头参数调整，不把“拉大 FOV”误当作碰撞修复。

这条路线比直接接入 Rapier / Ecctrl 风险低，能保护已有的 POI 边界、交互点、触摸控件和运行时 QA。

## 当前实现审计

### 直接观察

1. 主 Canvas 使用 `PerspectiveCamera`，初始垂直 FOV 为 `50`，`near=0.1`，`far=800 * environmentScale`（`app/xinhua-experience.tsx`）。Three.js 的 `fov` 是垂直视角，不是横向视角；窄屏上同一垂直 FOV 会得到更窄的水平视野。
2. 探索相机当前使用 `cameraGoalOffset`、`cameraOffset` 和指数阻尼；角色移动后相机会向角色后方回正。
3. 相机避障只在 X/Z 平面检查候选镜头端点与“角色—镜头”投影视线。先沿理想臂长缩短 16 步；失败后依次尝试 5 个 yaw 和 6 个半径，再尝试上一帧合法点和一个近身兜底点。
4. 角色碰撞与相机遮挡已经使用独立的 `WORLD_OBSTACLES` / `WORLD_CAMERA_OBSTACLES`，是正确的分层基础；角色移动是显式多边形边界与扩张 AABB 的分轴滑动。
5. 摇杆输入已有径向死区（`0.18`）和连续 `moveX/moveY`，没有退化成四方向布尔移动。
6. 但在摇杆持续激活时，`driveSignature` 固定为 `"analog"`，因此 `moveCameraForward` / `moveCameraRight` 只在“开始推杆”时抓取一次；之后相机自动回正或玩家拖动右侧视角，移动参考系不会随之更新。

### 基于源码的高置信推断

- 建筑旁快速转身时的“奇怪跳镜头”，主要不是单一碰撞盒错误，而是候选机位在“缩臂 → 多 yaw 搜索 → 历史安全点 → 近身兜底”之间切换；这些状态改变了相机方向而非只改变距离。
- 端点与二维视线即使都合法，真实相机的 near-plane / 画面体积仍可能擦过立面，因此会出现边缘裁剪、前景突然占满画面或角色被遮住。
- 摇杆左右/后方不跟手的主要来源，是持续模拟输入时参考相机方向被冻结；角色转身阻尼会进一步放大这种主观延迟。该判断须以运行时输入/方向调试叠层复核，但源代码路径明确支持这一假设。

### 尚未确认

- 哪些具体建筑或相机遮挡盒首先触发失败；需要录制路径与调试可视化，不应凭感觉扩大所有碰撞体。
- 目标手机的纵横比、帧率、低端 GPU 情况及玩家实际使用横屏/竖屏的比例；它们决定最终 FOV 和相机臂长参数。

## 外部资料可迁移原则

### Spring arm，而非单根射线

Godot 官方把第三人称相机组织为 pivot → SpringArm → Camera：沿预期臂长扫掠形状，发生碰撞后将相机放在接触点前；官方明确指出只用 ray cast 对相机碰撞不够准确，球体是平滑滑过边缘的常见选择。`camera-controls` 的 `colliderMeshes` 也会从相机 near plane 四角发射 4 条射线，而不是只用中心点。

对本项目的迁移：不需要引入 Godot 或 `camera-controls`，而是在当前代码中维护 `desiredArmLength`、`resolvedArmLength` 和 `occluderId`。先用现有二维障碍物做“圆形相机体”连续扫掠；只有楼梯、曲面池边、栏杆等少数不规则 POI 才升级到单独 collision-only mesh + BVH。

### 物理控制器仅作对照，不作第一步依赖

Ecctrl 的公开源码展示了 ShapeCast、触摸输入和可替换输入 UI，但同时要求 Rapier 和新的控制器生命周期。它证明“输入 UI 可以独立于控制器”以及“形状检测可优于单点 ray”的方向，不构成把当前街区整体迁移到 Rapier 的理由。

`three-mesh-bvh` 可提供 `raycastFirst` 和 `intersectsSphere` 等局部空间查询；它适合作为局部不规则碰撞的后续工具，但不能全局改写所有可见网格或承担本轮摇杆修复。

## 推荐架构

```text
左摇杆 / 键盘 ──> input vector（连续、可观测）
右侧拖拽       ──> desired camera yaw / pitch
                         │
角色移动 <── 每帧当前 camera yaw 的平面基向量
                         │
角色朝向 <── 受最大角速度约束的 desired move heading
                         │
shoulder pivot ──> desired spring-arm vector ──> shape sweep
                                                   │
                                             resolved arm length
                                                   │
                                      camera position + near-plane safety
                                                   │
                                  近距离仍遮挡？──> 局部遮挡物 dither/fade
```

关键原则：**用户输入控制 yaw/pitch；碰撞只控制臂长；可见性效果只处理遮挡物。** 三者不能再互相抢控制权。

## 分问题方案

### 1. 建筑旁相机遮挡与裁剪

#### P0：把现有二维方案改成稳定的“压缩臂长”

保留 `WORLD_CAMERA_OBSTACLES`，新增一个返回首个命中距离/法线的 swept-circle 查询：从 shoulder pivot 沿理想相机方向扫一个半径约 `0.22–0.30` 的圆，而不是逐帧枚举侧向 yaw。将命中距离减去安全边距后作为目标臂长。

- 碰撞时臂长快速收缩（例如 `lambda 24–32`）；恢复时缓慢拉回（例如 `lambda 5–8`）。
- 角度、角色目标点、肩位偏移保持不变；这样角色绕建筑转动时不会突然切到另一侧。
- 只在连续若干帧无命中后才更换缓存的 blocker / 恢复长度，避免墙角来回抖动。
- 用独立 `cameraRadius` 和 `cameraMargin`，不能复用玩家 `PLAYER_RADIUS`。

#### P1：最低臂长的可见性兜底

当可用臂长低于产品定义的最短舒适距离时，优先维持可控镜头并对“角色与相机之间的前景遮挡物”做局部 dither/fade；这与 Wiki 中已记录的 Summer Afternoon 类“百叶窗”遮挡思路一致，但本项目实现必须单独验收。

- 只作用于被相机视线命中的建筑 facade / 树冠片段，不改整栋建筑透明度。
- 用 dither / alpha-test 或临时隐藏小片段，避免普通半透明带来的排序、阴影和 SSAO 问题。
- 不对道路、地面、POI 交互物、角色自身、玻璃等对象开启该逻辑。

#### P2：局部 3D 查询，而非全局物理化

当二维 AABB 无法描述某个有台阶、围栏或弧形水岸的 POI 时，为它创建低面、不可见的 `camera-collision-only` GLB。使用 `three-mesh-bvh` 的首命中 ray/sphere 查询，仅服务这个 POI 的镜头和角色碰撞。每个 POI 独立审计和回归，不覆盖现有街区碰撞。

### 2. FOV

当前 `50°` 是垂直 FOV。建议先将探索态试验值提高到：

- 桌面 / 横屏：`56–60°`；
- 竖屏触摸设备：`60–64°`，同时将默认相机距离降低约 `5–10%`，防止角色在屏幕中缩得过小；
- 不建议直接跳到 `70°+`，广角畸变会使近处建筑边缘变形，并放大建筑贴脸时的不适。

FOV 必须按 viewport 以 `camera.fov = value; camera.updateProjectionMatrix()` 设置和验收。FOV 变大后，near plane 仍需维持合理的小范围（目前 `0.1`）；不要通过把 `near` 设得接近 0 来“修复裁剪”，这会恶化深度精度。

建议定义一个按 aspect 的产品函数，而不是固定常数：以 `58°` 为 landscape 基线、以 `62°` 为 portrait 上限，并在 390×844、844×390、1024×768、1440×1024 四个视口截图比较。若产品坚持竖屏的更大横向信息量，应配合更高的相机位与小地图/兴趣点提示，而不是强推极端 FOV。

### 3. 摇杆与转身手感

#### 必做修复：每帧使用当前相机平面

移除 `driveSignature === "analog"` 的一次性基向量缓存。移动向量应始终由当前 `cameraForward/cameraRight`（投影到地面）计算；为避免相机自动回正造成轻微漂移，可以对“输入参考 yaw”做很轻的、每帧更新的阻尼，而不是只在推杆开始时固定。

这会直接修复：先向前推杆、再把摇杆拨到左/右/后方时，角色方向仍以旧相机朝向计算的问题。

#### 手感参数与交互分工

1. 左摇杆只决定移动方向与速度；右半屏拖拽只决定相机 yaw/pitch。两根手指同时使用时，两个状态互不覆盖。
2. 角色朝向以移动向量为目标：满摇杆时最大转向速度可先试 `540–720°/s`，使 180° 转身在约 `0.25–0.35s` 内完成；小摇杆则用较低角速度，保留走路的自然感。
3. 将摇杆径向死区从 `0.18` 分别试验 `0.12`、`0.15`、`0.18`；保持径向重映射，不改为 X/Y 布尔值。不要先凭手感决定，需用真机误触率与起步延迟选择。
4. 将速度曲线显式化：低幅度对应慢走，中高幅度平滑达到跑步；当前“接近边缘即 sprint”的阈值需要与角色转向、动画和坡面路径一起调，而非单独改 CSS 摇杆尺寸。
5. 右侧拖拽结束后，给相机约 `250–400ms` 的“手动控制宽限期”，再平滑跟随到角色后方；这避免刚看向街景就被自动回正抢走。

## 推荐实施顺序

| 阶段 | 改动范围 | 完成判据 |
| --- | --- | --- |
| 0：可观测性 | 仅开发调试叠层与路径录制 | 看得到输入向量、相机 yaw、理想/实际臂长、阻挡物 ID、候选状态；能复现三个问题 |
| 1：摇杆基准修复 | `PlayableWanderer` 的移动参考系、转向和手动镜头宽限 | 22.5° 间隔的全圆摇杆方向不再相对旧朝向偏移；左/右/后转可预测 |
| 2：FOV 试验 | 探索相机 FOV/距离参数与四视口截图 | 选定一个兼顾空间感、人物屏占比和建筑变形的档位 |
| 3：spring arm | 当前相机避障替换为连续压缩臂长 | 绕 L 型墙、贴墙倒退、快速 360° 转镜头时没有跳到无关 yaw 或历史位置 |
| 4：遮挡淡出 | 仅最短臂长时的 facade/tree occluder 视觉方案 | 角色不会被前景完全挡住，同时不出现整栋半透明和阴影异常 |
| 5：局部 BVH | 只选一个无法用盒描述的 POI | 与显式盒基线比较后，确认楼梯/栏杆收益大于包体和回归成本 |

## 运行时验收合同

每轮都在真实 `?start=` 页面执行，而不是只看单元测试。

1. **建筑背靠测试**：角色离 facade 很近，连续转一圈；相机可缩短但不瞬移到另一侧，不越墙，不持续遮住角色。
2. **L 型转角**：边移动边转镜头穿过内外角，记录臂长曲线必须连续；不得在两个 fallback yaw 间闪烁。
3. **反向摇杆**：保持摇杆激活并依次前、左、后、右各 1 秒；角色移动方向相对于当前相机的误差不超过 `8°`。
4. **快速转身**：满摇杆 180° 转向，记录角色视觉朝向达到目标 `90%` 的时间；桌面和 390px 真机分别测量。
5. **双指操作**：左手持续移动、右手拖动视角；松开右手后相机延迟回随，左手移动不被中断。
6. **FOV 视口矩阵**：390×844、844×390、1024×768、1440×1024；核对人物屏占比、近景建筑变形、POI 可读性、near-plane 裁剪与 FPS。
7. **性能**：同一条 30 秒路径、同一 DPR/可见性/预热条件，记录平均/1% low FPS、长任务、首屏资源和 WebGL 错误。没有同条件基线，不声称性能提升。

## 不建议做的事

- 不直接把 `ecctrl` / Rapier 当作“摇杆手感修复包”；它会改变角色、碰撞和相机生命周期，超出当前问题范围。
- 不继续增加更多 fallback yaw 或把 `lastSafeCameraPosition` 当主策略；这只会增加瞬移分支。
- 不把所有可见建筑 GLB 变成全局 BVH，也不全局覆写 `THREE.Mesh.prototype.raycast`。
- 不用极端 FOV 或极小 near plane 掩盖遮挡问题。
- 不把摇杆重新降级成四方向布尔状态。
